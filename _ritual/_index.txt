TWO REAL BUGS FOUND WHILE PROVING IT (both fixed, both were disguised as "driver broken"):
  1. PS5 hex-literal cast.  0x8A702004 / 0xC0000000 parse to a NEGATIVE Int32 in PS5 and
     [uint32]<hex literal> then throws "Value was either too large or too small for a UInt32"
     (0x8A702004 -> -1972363260).  p26_drv.ps1 died on it silently because nothing captured its
     error stream - that is why its IOCTL block printed blank handle/ok lines while the service
     looked fine.  Fix: decimal literals, and derive IOCTL_PROBE = IOCTL_VERSION + 4.
     RULE: never write [uint32]0x... in PS5.
  2. ABI PACKING.  The driver TU inherits #pragma pack(4) from <ntddk.h>/<ntifs.h>/WDM headers;
     user mode keeps pack(8).  So sizeof(APEXDRV_PROBE_REQUEST) was 84 in the driver vs 88 in
     the launcher -> the two ULONG64 trailer fields sat 4 bytes apart and user mode parsed a
     garbage PEB address (the "Information=84 vs sizeof=88" line in the log was the tell).
     include\apex_driver_ioctl.h now pins `#pragma pack(push,1) ... #pragma pack(pop)` around the
     two structs.  pack(1) reproduces the DEPLOYED layout exactly (84 bytes; PebAddress 36,
     RemoteAllocation 44, Bytes 52) so NO driver rebuild/re-flash is needed, and
     apex_launcher.c's PROBE parser is corrected by the same edit.
     APEXDRV_INJECT_REQUEST is pack-insensitive (552 both layouts).  Probe scripts use 36/52.
     STILL OPEN (optional): rebuild apexdrv + apex_launcher to lock the pinned layout into
     artefacts; the running .sys is the pre-pin build but is layout-identical to what the pin
     now declares.
