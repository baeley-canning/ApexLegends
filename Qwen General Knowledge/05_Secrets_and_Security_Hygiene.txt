SECRETS AND SECURITY HYGIENE
============================
Purpose: keep API keys, passwords and personal data safe while developing.

1. WHAT COUNTS AS A SECRET
- API keys (OpenAI, DeepSeek, Anthropic, cloud providers), access tokens,
  passwords, private SSH keys, database connection strings, session cookies.
- Treat a key as money: anyone with it can run up charges or access data.

2. WHERE SECRETS SHOULD LIVE
- Environment variables, loaded at runtime:
    import os
    api_key = os.environ["DEEPSEEK_API_KEY"]   # KeyError if missing = good
- A .env file for local development, read with python-dotenv:
    from dotenv import load_dotenv; load_dotenv()
  The .env file must be listed in .gitignore.
- Commit a .env.example with the variable NAMES and dummy values so others
  know what to set, never the real values.
- OS credential stores (Windows Credential Manager, keyring library) or a
  password manager for long-term storage.

3. WHERE SECRETS MUST NOT LIVE
- Hard-coded in source files.
- In git history (even if later deleted).
- In folders synced to cloud storage (OneDrive Desktop/Documents, Dropbox,
  Google Drive) unless you accept the cloud provider holding a copy. On
  Windows, Desktop and Documents are often silently synced to OneDrive.
- In AI knowledge bases, prompts, chat logs or screenshots: models can repeat
  them and logs can be shared.
- In error messages or logs. Never print the key; print "key loaded: yes".

4. IF A KEY LEAKS
- Revoke/rotate it immediately in the provider's dashboard. This is the only
  real fix; deleting the file afterwards does not undo exposure.
- Check the provider's usage page for unexpected charges.
- Then remove it from files, history and synced folders.

5. GENERAL HYGIENE
- Least privilege: give keys only the permissions and spending limits needed.
  Set billing alerts and hard caps where providers allow.
- Separate keys per project so one leak is contained and easy to rotate.
- Keep OS, drivers, Python and packages updated.
- Install packages only from trusted sources; check names carefully
  (typosquatting: "reqeusts" instead of "requests").
- Be wary of running scripts or executables from unknown sources, especially
  anything asking for admin rights or disabling antivirus.
- Back up important work (git remote + a separate backup).

6. CODE THAT HANDLES USER INPUT
- Never build shell commands or SQL by string concatenation with user input.
  Use subprocess with a list of arguments, and parameterised SQL queries.
- Validate and limit file paths from input (no "../" escaping a folder).
- Don't use eval()/exec() on untrusted text, including LLM output.
- Treat LLM output as untrusted input: review generated code before running
  it, and never give a model unrestricted shell access to a machine holding
  important data.
