## APEX AIMBOT - Session Learnings (2026-10-04)

### 1. GPU Inference - Evidence Tracking

**FACT:** CUDA available, model placed on `cuda:0` (RTX 5060). Verified by `next(model.parameters()).device == cuda:0`.

**FACT:** Actual GPU benchmark completed: **105.6 FPS inference** at 640x640, 9.5ms latency per frame on NVidia GeForce RTX 5060. This is YOLOv8n (nano) - the smallest model.

**HYP:** The earlier ~15 FPS end-to-end pipeline speed was NOT purely CPU inference. It's a composite of: capture -> preprocessing -> CPU->GPU transfer -> GPU inference -> GPU->CPU transfer -> postprocessing -> tracking -> logging. Any stage could bottleneck.

### 2. Detector <-> Tracker Format Mismatch (CRITICAL BUG - FIXED)

**Bug:** `detector.py` output detections with separate keys (`x_min`, `y_min`, `x_max`, `y_max`) but `tracker.py` expected a single `bbox` list `[x_center, y_center, width, height]`. Every detection was silently dropped because `det.get("bbox")` returned empty.

**Fix:** Added computed `bbox: [cx, cy, w, h]` to detector output alongside the individual coordinate keys. Both tracker and visuals now work.

### 3. Tracker - New Track Predicted Center (BUG - FIXED)

**Bug:** When a new track was created from a detection, `track.predicted_center` stayed at default `(0.0, 0.0)` because only `kalman.x[:4]` was set but not `predicted_center`. On frame 2, the association cost from (0,0) to the actual target position exceeded `max_distance`, causing ID switches every frame.

**Fix:** Set `track.predicted_center = (float(measurement[0]), float(measurement[1]))` at track creation time so first-frame association works correctly.

### 4. OpenCV GUI - Reinstall Required

**FACT:** Original `opencv-python` was built with `GUI: NONE` - no debug window possible. Reinstalled full `opencv-python` (v5.0.0.93) which has `GUI: WIN32UI`. Debug windows now render.

### 5. Recursive Window Capture (FIXED)

**Root cause:** MSS captured the entire desktop including the OpenCV debug window, which then appeared inside itself recursively - dozens of nested copies.

**Fix:** Fixed-position overlay at `(10, 10)` with small size `320x240` so it doesn't capture itself. Like Ignite/KernAim cheats - fixed corner position, not moveable.

### 6. Kalman Filter Behavior (TESTED)

**FACT:** Constant velocity tracking works correctly - estimated +5.0 px/frame matches true +5.0 px/frame.

**WARN:** Prediction during occlusion shows drift of ~25px over 9 frames when initialized with `kf.x[4]=5.0`. This is because the Kalman filter's initial velocity guess gets corrected by early measurements, then prediction uses the corrected (lower) velocity. Not a bug - expected Kalman behavior. The filter converges to true velocity after ~3-5 updates.

**Recommendation:** Initialize `kf.x[4] = 0` and let the filter learn velocity from data rather than guessing. Or increase `process_noise` to allow faster velocity adaptation during occlusion.

### 7. Tracker ID Persistence (TESTED)

**FACT:** With the predicted_center fix, a target maintains its ID across frames when moving at constant speed within `max_distance`. Without it, IDs switched every frame because predictions from (0,0) never matched detections near (960, 540).

### 8. Predictor Extrapolation (TESTED - EXACT)

**FACT:** Linear extrapolation is mathematically exact: position + velocity x frames_ahead = predicted position. No error. This confirms the predictor implementation is correct.

### 9. Tracker Expiration (TESTED)

**FACT:** Tracks correctly expire after `max_age` frames without detections. After 10 frames of detection with `max_age=5`, there are 5 active tracks (one per frame's contribution). After 11 frames of no detections, all are gone. This is correct behavior.

### 10. End-to-End Pipeline (TESTED)

**FACT:** Full pipeline processes a target that moves -> gets occluded for 8 frames -> reappears at a new position. Tracker maintains ID during movement and occlusion, reassociates on reappearance. No crashes or errors.
