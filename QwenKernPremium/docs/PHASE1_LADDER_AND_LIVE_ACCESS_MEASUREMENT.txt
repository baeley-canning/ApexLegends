1. WHAT WAS BUILT (and how to run it)
--------------------------------------------------------------------------------
* Launcher strategy LADDER (PHASE 1.2): rungs are tried least-invasive-first -
  sticky rung first, then A3 (APC), A2 (NtCreateThreadEx), A1 (CreateRemoteThread
  + LoadLibraryA), then B3 (kernel driver, SKIPped while apexdrv.sys is absent).
* VERDICT RULE: a rung only counts when the payload DLL shows up in the target's
  module list. The injector's own "success" is NOT the verdict - an APC queues
  successfully long before the DLL exists, which is exactly how a cheat gets
  fooled.
* VERIFICATION WINDOW (kVerifyWindowMs = 3000): the module list is polled for up
  to 3 s after the injector returns. Without this, A3 was reported FAIL even
  though it loaded the payload in 47 ms - a measurement bug, not a real failure.
* STICKY per-machine rung: <launcher dir>\apexcheat.launcher.ini, written ONLY
  after a VERIFIED pass, read on the next run and tried first. --no-sticky turns
  the file off; --forget-sticky deletes it (menu key '6' toggles it too).
* REFERENCE INTEGRITY (PHASE 1.3): before injecting we record the target image
  name, module base + PE-header readability, module count and the render-module
  state (d3d11/dxgi/d3d12/d3d9) so "d3d11 is loaded" can never be our own doing.
* "Measuring instrument" check: if the target's module list is not readable, the
  ladder says so loudly instead of reporting a wall of false FAILs.

  run:  apex_launcher.exe                     (interactive menu)
        apex_launcher.exe --inject --no-wait  (ladder once, exit 0 = verified)
        apex_launcher.exe --method=crt|nt|apc|kernel   (force ONE rung, no sticky)
        apex_launcher.exe --probe [--pid=<pid>]        (measure, never inject)
        apex_launcher.exe --forget-sticky | --no-sticky

11.1 The handle is NOT the wall, and the integrity level split is clean.
h322 (medium IL, PID 29300) is the row that kills the "our token is wrong" theory
in the other direction: at medium IL the game's DACL/section denies everything
except QUERY_LIMITED and SYNCHRONIZE.  h323 (elevated, PID 29184) is granted
0x1F0FFF on the first try.  So the ladder's old sentence "OpenProcess(ALL) OK"
is true only ELEVATED, and elevation is a hard precondition, not a nicety.  It
is also worth keeping: an elevated handle is granted but still useless, which
means the denial is applied BELOW the handle, per call.

11.2 The address space visible through that handle is the GAME'S REAL ONE.
h327 walked the target's VAD from address 0 to 0x7FFFFFFFFFFF with
VirtualQueryEx and a same-run self-control (the probe censuses its own process
first, with the same code, and that control passes - the instrument is trusted):

  self  : 1922 regions, 298 MB commit, 1297 image sections, walk 4 ms
  game  : 9492 regions, 11364 MB commit, 7737 MB working set,
          1765 image sections / 577 MB image, 8724 MB private,
          2061 MB mapped, 5232 MB reserve, commit/ws = 1.47
          r5apex_dx12.exe image section at 0x140000000, size 0x11F0000,
          protection 0x404 (EXECUTE_READWRITE + MEM_IMAGE)
          lowest image section 0x1D10000 .. 0x209C000 (PAGE_EXECUTE_READ)
          PEB reported by NtQueryInformationProcess = 0x20F000, and the VAD
          confirms it: MEM_IMAGE, committed, protection 0x4 (PAGE_READWRITE)

1765 image sections is the whole module set (Apex loads ~60 modules plus
thousands of mapped images), 11.1 GB of commit is a running DX12 game, and the
PEB lands on a real committed RW image page.  A manipulated DTB / shadow CR3 /
"fake VAD" presentation could not produce that.  The shadow-address-space theory
is therefore RULED OUT, and with it the whole class of "we are reading the wrong
CR3" fixes.

11.3 So why do reads fail, and why is every module list empty?
Both have the same cause: the filter sits on the DATA-TRANSFER calls, not on the
information calls.  VirtualQueryEx, NtQueryInformationProcess and the section
walk are answered from kernel bookkeeping and are granted; ReadProcessMemory,
WriteProcessMemory, VirtualAllocEx and NtAllocateVirtualMemory are refused
(87 / 5 / 0xC000000D / 0xC0000022, all different, which is a parameter-sensitive
check and not one blanket "deny").  Reading the committed PAGE_READWRITE PEB page
still returns 87, i.e. the refusal is unconditional with respect to the page.

That also explains the ENTIRE X8/I0 mystery of section 4 and the "before" of
section 3: every module list in the tree comes from the PEB LDR list, and the
PEB is unreadable, so psapi/EnumProcessModulesEx and Toolhelp both report 0
modules while the VAD says 1765 image sections.  "Zero modules" was never
evidence that the game hides its modules; it is evidence that RPM is blocked.
The two measurements agree once the access path is named - and that means a
module-base lookup can still be had from the VAD-side information ops, which is
the first genuinely new primitive this re-measure produced.

    OpenProcess err=5 (it ran at medium IL, 13:55:14).  So the external-suspend
    hypothesis is UNTESTED, not disproved.  What is measured is the other half:
    ov62/ov64/ov65 all died at 0x186AA (100522) from a CREATE_SUSPENDED launch
    with NO patch at all, so the abort is the game's own post-resume watchdog and
    not an anti-cheat kill.  Consequence: any "launch suspended, inject, resume"
    rung is dead on this title regardless of what we inject.

11.5 What the filter looks like, stated as a falsifiable shape.
Parameter-sensitive denials (four distinct codes for four alloc parameter sets),
granted information queries, granted OpenProcess at high IL, unconditional denial
of the copy calls at a committed RW page.  That is an IOCTL/ob-callback or
syscall-hook filter with a rule table keyed on (call, access, protection) - not a
rights strip and not an address translation.  Predictions it makes, for the next
probes to falsify: (a) a read-only driver copy bypasses it (different call path,
own MDL); (b) a thread-context hijack is NOT covered, because
SuspendThread/Get/SetThreadContext are process-manager ops and the process handle
already grants SUSPEND_RESUME; (c) anything routed through the loader inside the
game still resolves through an unreadable PEB.

11.6 What this does to the strategy (the actual decision).
The old ordering put the kernel rung last as a fallback.  The measurements
invert it:
  - user mode: every mutating call is refused, but the game never dies.
  - kernel:   the calls land, but the target dies (h316: Javelin exit
              0x322327458D1ED790 ~2 s after the driver was armed; h318/h319: the
              real payload dies at step 7 with 0xC0000006, and allocation works
              only in the first 1-2 s of the process, 0xC000000D after).
  So "kernel injection" is no longer the safe fallback; it is the most dangerous
  rung in the tree, and h279 shows why it is not finished either: the stub DID
  execute with the right argument (entered=0x4870, RCX == remoteBase) and the
  loader call inside the game still failed - consistent with (c) above.
Ranked by (measured survival) x (measured capability):
  A. EXTERNAL, reads only.  Driver reads + h327's VAD-derived module bases + the
     overlay in its own window (ov56 renders against live Apex).  Nothing is
     written into the process, so nothing of ours can be the thing that kills it.
     This is the architecture the product already declares, and the only line
     with both a live-game PASS and a live-game read path.  Correction to the
     first draft of this paragraph: that read path is NOT proven by the
     h279/h318 out-block alone.  h323 (00:20:41, _ritual\h323_fire_ioctl.out)
     is a dedicated kernel read of the live game's PEB - MmCopyVirtualMemory
     status 0x0, copied=32, peb=0x2EC000, on pid 22756 - and the game was
     ALIVE 60 s later.  So "the driver reads game-private memory" is measured,
     once, on a live instance.  What is still unmeasured is duration, volume
     and arming order: that read was ~1 s after launch, in a run where the
     driver was armed BEFORE the game started (svc STATE 4 RUNNING at 00:18,
     pid detected 00:20).  A multi-KB read per frame, minutes into a match,
     with the driver armed first, is exactly what h329 measures.
  B. PRE-LAUNCH plant, loader maps it.  Zero handle writes, zero kernel writes;
     the loader does the mapping.  Untested, and Javelin watches file reads
     (section 8.3) - so it must be an added search-path DLL, not a modified game
     file.
  C. KERNEL manual map (v13).  Blocked on localising the step-7 death: map with
     no entry first, watch for minutes, then entry.  Do not arm it on the host
     before that is measured in the VM (R1).  h323 already splits that death
     one step further: a transient alloc+write+free into the live game (8 ms,
     freed, nothing resident) returned every status 0x0 and the game was ALIVE
     60 s.  So "kernel mutates the target" is NOT what kills it - what remains
     is residency and/or the entry call, which is precisely the pair that
     "map without entry" isolates.
The sentence in HANDOFF "the injected line wins" survives only for line B, and
only after it outlives a match.  A is what the numbers currently support.
