1. WHAT WAS BUILT (and how to run it)
--------------------------------------------------------------------------------
* Launcher strategy LADDER (PHASE 1.2): rungs are tried least-invasive-first -
  sticky rung first, then A3 (APC), A2 (NtCreateThreadEx), A1 (CreateRemoteThread
  + LoadLibraryA), then B3 (kernel driver, SKIPped while apexdrv.sys is absent).
* VERDICT RULE: a rung only counts when the payload DLL shows up in the target's
  module list. The injector's own "success" is NOT the verdict - an APC queues
  successfully long before the DLL exists, which is exactly how a cheat gets
  fooled.
* VERIFICATION WINDOW (kVerifyWindowMs = 3000): the module list is polled for up
  to 3 s after the injector returns. Without this, A3 was reported FAIL even
  though it loaded the payload in 47 ms - a measurement bug, not a real failure.
* STICKY per-machine rung: <launcher dir>\apexcheat.launcher.ini, written ONLY
  after a VERIFIED pass, read on the next run and tried first. --no-sticky turns
  the file off; --forget-sticky deletes it (menu key '6' toggles it too).
* REFERENCE INTEGRITY (PHASE 1.3): before injecting we record the target image
  name, module base + PE-header readability, module count and the render-module
  state (d3d11/dxgi/d3d12/d3d9) so "d3d11 is loaded" can never be our own doing.
* "Measuring instrument" check: if the target's module list is not readable, the
  ladder says so loudly instead of reporting a wall of false FAILs.

  run:  apex_launcher.exe                     (interactive menu)
        apex_launcher.exe --inject --no-wait  (ladder once, exit 0 = verified)
        apex_launcher.exe --method=crt|nt|apc|kernel   (force ONE rung, no sticky)
        apex_launcher.exe --probe [--pid=<pid>]        (measure, never inject)
        apex_launcher.exe --forget-sticky | --no-sticky

5. WHAT THIS MEANS (actionable)
--------------------------------------------------------------------------------
1. A1/A2/A3 are NOT "wrong methods" right now: they cannot even allocate in the
   target. Re-ordering the ladder will not help; the ACCESS has to be fixed.
2. B3 (kernel driver) becomes the PRIMARY rung: it needs no user-mode handle, no
   remote allocation and no readable module list, and it can map/read from kernel
   context where CR3 abuse does not apply. Budget: build+sign apexdrv.sys (see
   JAVELIN_2026 file, Path B; ERROR #119 denylist risk applies).
3. An EXTERNAL reader is blocked too (RPM fails), so "external overlay" is not a
   workaround on its own until reads work.
4. A7 (manual map) / A8 (VAD-less) stay gated on X2/X4 succeeding inside the
   target; the harness will say the moment that changes.
5. Reference-integrity output against a live game is currently "unknown" for the
   render modules because the module list itself is unreadable. Any claim of
   "d3d11 absent/present in Apex" made before this date is unverified.

Next actions (in order):
  a) re-run these measurements with the game at the MAIN MENU vs IN MATCH (ACG
     arming is stage dependent) and after a clean reboot (no stale EAC state);
  b) try NtOpenProcess / duplicated EAC handles and smaller masks (e.g.
     CREATE_THREAD|VM_OPERATION only) to see whether the denial is mask related;
  c) build apexdrv.sys (WDK is missing on this box) so B3 can be measured - the
     rung is already wired and only SKIPs on a missing file;
  d) check whether the launcher's session/integrity level relative to the target
     matters (run launcher as SYSTEM / from a service).

            A manual map that "failed" only because it is absent from the
            module list would be a measurement bug of the worst kind.

A7 manual map (src\manual_map.cpp), measured:
  image   : 344064 bytes -> 0x1BB67810000 (preferred 0x180000000)
  relocs  : applied for the real load address
  imports : resolved against the target's module bases (forwarders followed)
  entry   : thread 26348, exit 0x00000001 -> DllMain chain executed
  target  : alive, 94 modules, apexcheat NOT in the module list   <- the point
  ladder  : [1/7] A8 SKIP, [2/7] A7 PASS, sticky=A7, EXIT=0

A4 thread hijack, measured (same binary, two target kinds):
  sleeper : 27 threads hijacked, stub ran on 0  -> FAIL (all in ntdll waits)
  spin    : PASS, module present, hijacked thread RIP inside coreclr
  => "fails if the thread is a kernel wait" is now a measurement, not folklore.
  Fixes this run forced:
    * one 8 KB block (stub + CONTEXT + private stack) PER ATTEMPT.  A shared
      CONTEXT slot let an earlier, still-pending thread restore the LAST
      thread's registers.
    * a marker dword written by the stub's first instruction, so the log can
      say "stub never ran" instead of guessing from a module-list timeout.
    * per-thread verification, so a rung that does not deliver moves on.

Costs / limits recorded, not hidden:
  A7 needs VirtualAllocEx + a PAGE_EXECUTE* page in the target; on the live
     game X2/X3 refuse both, so the rung reports the win32 error verbatim.
  A7 pre-loads dependency DLLs with LoadLibraryA in the target (a DX12-only
     install would gain a d3d11.dll it never had - see Q14).
  A4 leaks one block per attempted thread (a pending thread may still run its
